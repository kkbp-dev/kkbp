# The graded templates take Shown Colours, ungraded in nodes

Updates [ADR 0041](0041-edit-templates-follow-the-games-shaders.md) and [ADR 0026](0026-edit-materials-dont-saturate-by-default.md). An edit template made from KK's or KKS's shaders takes the game's own colours, linear, and grades its light and dark at the end, as the maker camera does (`.KK grade`). So a colour input shows the colour the game stores, not the colour the material shows. The grade moves colours a long way: 0.12 per channel on average, up to 0.31. A grey of 0.5 shows as (0.39, 0.31, 0.37), and (0.8, 0.2, 0.2) shows as (0.82, 0, 0). A colour picked with Blender's eyedropper, from a reference image or from the scene, is a shown colour, and put into the input as it is, it comes out graded a second time.

A graded KK or KKS edit template now takes **Shown Colours**. Each colour its shader groups draw with is the colour the template shows for it, lit, on a white texture: the game's colour, graded. Inside each shader group, `.KK shown color` turns it back into the game's colour before the shader reads it: `linear(ungrade(srgb(colour)))`. `.KK ungrade` reads `Lut_TimeDay inverse.exr`, the grade's inverse. Edit Material's menu switches them: Default and On take Shown Colours, Off the game's colours, as before. The menu meant nothing to these templates until now, since they never saturate their textures; for them it is labelled **Shown colours**, and for a legacy template (a modded shader's), which it still saturates, **Saturate**. On by default, because an unedited edit bakes the same either way: on both Golden Samples, every KK and KKS edit material's light and dark came out at most 0.0002 apart (the tongue's dark), 0.00003 on average.

The grade moves each channel one way only and reaches every colour, so every shown colour has a game colour behind it. `importer/tools/make_ungrade_lut.py` solves for one per colour of a 32-step grid and writes the strip in the grade's own layout, as 32-bit floats; `.KK ungrade` reads it as `.KK grade` reads its LUT (`lut_nodes.lookup`). Where the grade clips strong colours, several game colours show alike, and the table gives back one of them.

Between its grid steps the table interpolates, which a colour picked by eye doesn't notice: on 3,000 random colours, what shows is 0.16/255 from the colour typically and 7.7/255 at worst. But near white the grade is flat in some directions, so a small step in the table is a large step in the game's colour: (0.918, 0.938, 0.958), the Golden Samples' shorts and bra, came back with a blue of 0.973. Clothes and hair tint their shadow by the colour's hue, which a near-grey colour barely has, so the shorts' dark bakes moved 0.010 further from the game (KKS: 0.025 to 0.035). Correction steps in the nodes barely help: the grade mixes the channels. So the edit tool doesn't write the graded colour: it solves for the colour the table turns back into the game's (`shading.shown_color`, a few Newton steps in numpy). That gives back every drawn colour of both Golden Samples exactly, including the ones the grade clips, and their swatches are within 7.3/255 of the graded colours. `blender/test_edit_accuracy.py` bakes every KK and KKS edit material both ways and holds each to the same recorded numbers.

## Considered Options

- **Colour fields in the KKBP material panel**, each converting to and from its socket when drawn and set: the sockets keep the game's colours, and nothing in the templates changes. But the colours stay in two places, the fields can't be keyframed, and the user wanted to set the colours where they are, in the node tree.
- **Shown Colours always, with no menu for them**: a colour the table can't give back (a strong colour no Golden Sample has) comes back only close, so an unedited edit's dark side could move; Off keeps the game's colours for that.
- **Shown Colours only with the menu On, Default keeping the game's colours**: the eyedropper is the reason for them, and an unedited edit bakes the same, so the default should be the one that lets it work.
- **One label for the menu**: Saturate says nothing about what it does for most materials now.
- **Shown Colours by default, switched by the menu, ungraded in each shader group (chosen)**: the sockets stay where they are, with the same names; the table read happens only for the colours a group draws with.
- **A converter node per colour in the material**, in front of the group input: the material tree gets a node per colour, and the colours move off the groups where the wiki says they are.
- **An 8-bit inverse table**: it would round the game colours it gives back, which the dark side's tint shows; a float EXR is half a megabyte.
- **A 64-step table, or correction steps in nodes**, in place of solving for the swatch: on near-white colours, either left the game's colour 0.015 to 0.02 off.
- **The graded colour as the swatch**: exact for what shows, but an unedited edit's near-grey colours come back off, as above.

## Consequences

- `shown_colors.route` gives each of KK's shader groups that draws with colours (`.KK create_topN`, `main_hair`, `main_item`, `toon_eyew`, `create_eyewhite`, `toon_nose`, `create_body`, `create_head`, `skin overlays`, `toon_eye`) a `Shown colors` input and a `.KK shown color` node per drawn colour. Each graded template with such a group has a `shown colors` Value node feeding them all, its `shown_colors` param. The shadow and specular colours are tints, not shown, and stay the game's.
- The KK profile's colour tables mark the drawn colours `shown`: a Shown Colour unless the menu is Off, the game's colour linear then. KKS inherits them. The inverse table is a library extra (`ungrade_lut`), which the edit tool reads to solve for each.
- An edit with Shown Colours is marked saturated (`kkbp_edit_saturated`), so Reset keeps the choice, as it keeps saturation. Its textures are still never saturated.
- The panel labels the menu by `edit_material.menu`, which looks the material's template up in the bundle once per material; its tooltips follow (two item lists with the same identifiers). SVS's materials, for which it does nothing, show no menu.
- SVS's templates have no grade (ADR 0051) and so no Shown Colours: the menu still means nothing to them. The legacy templates still saturate with it, and don't by default.
- Each drawn colour reads the inverse table: eight more texture reads per pixel. Measured on KK's face and a shirt, with Shown Colours on and off, their bakes (Eevee compiling the shader included) took the same time, 0.5 to 0.9 s on both Blender builds.
- The template version is 3, so a file that has the older groups appends the new ones beside them.
- A Shown Colour is the colour of a lit, white area. A clothing texture with shading in it shows darker than the colour where it isn't white, so a colour picked from such a pixel of a render comes out darker; the eyedropper needs the Standard view transform, which the import sets.
